## 无损压缩实测（仅代表样本，不是全库预测）

直接压缩原始文件字节，不解析或重新写出 JSON；无舍入、无坐标转换、无抽稀、无删字段、无 SID 数值转换。

|---|---:|---:|---:|
| 北京分片 | 20,101,943 | 3,744,095 | 3,599,488 |
| 南京分片 | 18,297,190 | 3,312,187 | 3,203,802 |
| 杭州分片 | 18,104,024 | 3,736,452 | 3,623,600 |
| 重庆分片 | 17,069,568 | 3,744,376 | 3,660,839 |
| 呼和浩特分片 | 16,795,973 | 3,627,213 | 3,555,438 |
| 昆明分片 | 20,171,091 | 3,845,034 | 3,697,633 |
| 全部隐藏数据 | 39,284,602 | 5,639,573 | 5,308,009 |
| 集合元数据 | 70,090 | 11,176 | 10,963 |
| **合计** | **149,894,481** | **27,660,106** | **26,659,772** |

- gzip6 节省 **81.55%**；gzip9 节省 **82.21%**。
- 所有 16 个 gzip 产物均逐块解压，逐字节等于源文件，SHA-256、字节数相同，源文件未改动；输入块最大 1 MiB。
- gzip9 比 gzip6 产物再小 3.62%，本机压缩时间约 10.39 秒 vs 5.34 秒；这些时间不是浏览器实测。
- 原始十进制文本逐字节恢复，故现有坐标精度、SID、时间、道路等字段均保持。
- 三个可选样本的 XZ/bzip2 和 gzip 再压缩也完成一致性校验，总计 23/23；XZ 更小但浏览器无内置 XZ 解压，适合离线归档，不作为当前发布首选。

完整结果、SHA-256 和可复现测量脚本保存在本地 Downloads 下 `compression-review-20261107`，不提交样本压缩件或本机绝对路径敏感配置。

## 推荐发布方案（当前尚未转换全部存量）

**首选：保留原始源数据，发布层逐分片 gzip。**

1. 在独立的干净发布目录生成每个点位分片的 `.gz`，使用固定 gzip 时间戳，保持构建可复现。
2. 每个文件保存原始长度与 SHA-256；构建时解压逐字节校验，失败就停止发布。
3. 发布目录只包含前端、必要小元数据/网格和压缩数据。不能同时发布全部原始 `.js` 和 `.gz`，否则只是增大站点。
4. 改造分片加载器：按需 `fetch` 压缩数据，以 `DecompressionStream('gzip')` 解压、验证长度与哈希后再装载原脚本/数组。隐藏数据加载也要接入同一流程，不能拆坏红色与游戏集合。
5. 做功能检测；旧 WebView 需要回退解码器或明确兼容提示。`.gz` 不能直接当普通 `script.src`，也不能因服务器已应用 `Content-Encoding` 再重复解压。
6. 保持按城市懒加载；压缩减少存储和传输，不会减少解压后 JS 数组的内存。
7. 先测单市与全部隐藏集合，再完整构建、比较源字节/点数/唯一 SID，最后才切换部署；不靠压缩 ZIP 二次压缩解决问题。

[MDN DecompressionStream](https://developer.mozilla.org/en-US/docs/Web/API/DecompressionStream) 给出浏览器 API 与支持信息。当前只完成实测与方案，不冒然改变全部四千万点的存储格式或托管位置。
