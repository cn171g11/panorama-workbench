# 腾讯隐藏街景/时光机：常规街景混入清理

网页版本: `v1.0.15`（2026-10-24）

## 问题

「腾讯隐藏街景/时光机」合集里混入了**能自由移动的常规街景**，另有 2 条坐标落在 `0,0` 的非法记录。
用户给出的判据：**能移动 = 常规街景（应删除）；不能移动 = 隐藏街景（保留）；剑灵游戏街景为例外。**

## 根因

缺口扫描（gap scan）把「时间缺口内返回了普通元数据的点位」记为 `normal-in-gap` 候选，
导入工具 `tools/merge_gap_scan.py` 只校验坐标、不校验可移动性，于是把这些常规街景一起写进了隐藏合集。
所以混入全部集中在做过缺口扫描的南京及周边（南京 + 溧水两次扫描），其余城市的历史记录没有这个问题。

## 判据实现

移动性判定模块 `tools/pano-mobility.js`（规则版本 `navigation-v1`），对每个点位实时请求
`https://sv.map.qq.com/sv?svid=<id>&output=json`，只有以下来源才算「可移动」：

- `detail.roads[].points` 中当前点位的**前/后相邻帧**
- `detail.vpoints[]` 中 `svid` 命中当前点位的 `link[]` 相邻帧
- `detail.all_scenes` 中的序列相邻帧（仅取相邻位，不把历史切换当作通行）

以下情况不算可移动：邻接 id 等于自身、邻接为 `0,0`、坐标为 `0,0` 或越界、元数据报错、`svid` 不匹配。
剑灵（Blade & Soul）示例点位在 `tools/data/tencent-game-exceptions.json` 中登记为例外，永不据此删除。

## 审计结果

| 项 | 数值 |
|---|---|
| 审计点位 | **2,044** |
| 判定为隐藏（不可移动） | 1,794 |
| 判定为常规（可移动） | **250** |
| 覆盖来源 | 南京缺口扫描 1,236 + 溧水缺口扫描 828，去重后 2,042，另抽查 2 条历史记录 |

250 条待删记录的地理范围：经度 **118.4825–120.4788**、纬度 **30.7513–32.3870**，
即南京城区、镇江—扬州一线，最远一条在浙江乌镇（`180330X3131016142337100`，实测 2 个相邻帧）。
与「问题都在南京及周围延伸」的判断一致。

## 清理结果

| 项 | 数值 |
|---|---|
| 清理前 | 19,958 点 |
| 清理后 | **19,706 点** |
| 移除合计 | **252** |

## 防止再次混入

`tools/merge_gap_scan.py` 的导入路径改为**要求移动性证据**：

- 有审计记录时，必须 `status=hidden && canMove=false && movementCount=0` 才允许导入；
- 没有审计记录时，只接受记录内联了同等字段（`isMobilityVerified` / `verificationRule` / `movementCount`）的点位；
- 坐标非法（含 `0,0`）一律拒绝；
- 未提供 `--verification` 而出现被排除记录时，会打印显式告警，避免「静默加了 0 个点」。

审计结果沉淀为基线文件 `tools/data/hidden-collection-verification.json`（2,044 条），
`purge_hidden_collection.py`、`build_hidden_viewer_data.py` 默认读取它。
测试：`tools/tests/test_hidden_collection_rules.py`（6 项）、`tools/tests/pano-mobility.test.js`（7 项）全部通过。

## 已知边界（诚实说明）

- 本次只核验了与缺口扫描相关的 **2,044** 条；合集里其余 **17,914** 条历史记录**没有重新核验**，按原样保留。
  若后续怀疑其他城市也有混入，需要对相应范围再跑一次移动性审计。
- 判据基于腾讯元数据的邻接关系，属于**服务端视角的可移动性**；元数据缺失邻接、但客户端实际可移动的极端情况无法识别。
- 2 条 `0,0` 记录按用户要求直接删除，未尝试反推其真实坐标（`02034100001411031437596106A` 原始标注为「莫高窟 MGK」）。
